# Data

*Data source, preprocessing pipeline, naming conventions, and normalisation constants for the SAR DDC project.*

## Source

TerraSAR-X StripMap (SM) Single Look Slant Range Complex (SSC) images, downloaded from [ESA's platform](https://earth.esa.int/eogateway/catalog/terrasar-x-esa-archive).

> Access requires submitting a form; expect 1–2 business days for approval.

The raw CoSAR `.cos` files are placed under `data/TSX_cos_files/` (the `data/` directory is git-ignored; use symlinks to avoid multiple copies of large files).

## Preprocessing Pipeline

### 1. Compute normalisation statistics

`scripts/dataset/compute_stats.py` implements Welford's online algorithm to compute running statistics (intensity and log-amplitude mean, variance, and percentiles) over all CoSAR images, without loading the full dataset into memory. Run this once before creating training sets:

```bash
cd scripts/dataset
python compute_stats.py > ../../data/analysis/dataset_stats.log
```

The resulting percentile values are used to derive the global normalisation constants stored in `src/utils/constants.py` (see [§ Normalisation constants](#normalisation-constants)).

### 2. Create HDF5 patch datasets

`scripts/dataset/create_dataset.py` processes the raw `.cos` files into HDF5 patch datasets convenient for training. For each `.cos` file it:

- Loads the raw complex SAR data via `load_cosar()` (I/Q channels)
- Symmetrises the complex image following the MERLIN convention
- Extracts non-overlapping `patch_size × patch_size` patches (`stride = patch_size`)
- **Training split** (`train.h5`): patches stored raw, shuffled out-of-core via chunked processing
- **Val / test splits** (`val.h5`, `test.h5`): additionally runs ADAM-NOC and MERLIN inference to generate linear-amplitude ground-truth channels

```bash
python scripts/dataset/create_dataset.py \
    --input-dir data/TSX_cos_files/ \
    --output-dir data/processed_hdf5/ \
    --split-file data/TSX_cos_files/spatial_splits_5.json \
    --patch-size 256 \
    --seed 42
```

Use `--help` for the full option list.

Patches are stored **raw** (no normalization). Log-amplitude normalisation is applied by the `LightningDataModule` at training time.

### 3. Convert test split to NumPy for FPGA evaluation

`scripts/dataset/convert_h5_to_np.py` extracts the test-split patches from an HDF5 file into a single `.npy` array — the format expected by the FPGA inference binary (`build_cpp/inference_hybrid`).

```bash
python scripts/dataset/convert_h5_to_np.py \
    --dataset_path data/processed_hdf5/TSX_spatial_splits_5_256x256/test.h5 \
    --subset 500 \
    --seed 42
```

The `--subset N` argument randomly samples N patches (reproducible via `--seed`). The output file is written next to the source `.h5` with the name `<stem>_sub<N>_seed<seed>.npy`.

## Output Structure

Each call to `create_dataset.py` creates a subdirectory named `TSX_<split>_<patch_size>x<patch_size>/` inside `--output-dir`, containing three HDF5 files:

```text
data/processed_hdf5/
└── TSX_<split_file_stem>_<patch_size>x<patch_size>/
    ├── train.h5
    ├── val.h5
    └── test.h5
```

For example, `--split-file .../spatial_splits_5.json --patch-size 256` produces `TSX_spatial_splits_5_256x256/`.

### HDF5 schema

All files store a single `patches` dataset of `float32` values.

| File | Shape | Channel layout |
| ---- | ----- | -------------- |
| `train.h5` | `[N, H, W, 2]` | 0: raw real (I), 1: raw imaginary (Q) |
| `val.h5` / `test.h5` | `[N, H, W, 4]` | 0: raw I, 1: raw Q, 2: ADAM-NOC lin. amp., 3: MERLIN lin. amp. |

Patches are stored **raw** (no normalisation). Log-amplitude normalisation is applied by the `LightningDataModule` at training time.

Ground truths (channels 2-3) are in **linear amplitude** — generated by running each reference model on the normalised input and reversing the normalisation. See `src/utils/constants.py` for `AMP_MIN`/`AMP_MAX`.

HDF5 metadata (in `dset.attrs`): `creation_date`, `seed`, `split_file`, `patch_size`, `nb_patches`, `patches_per_image`.

## Visualisation Folder Naming Convention

`data/visualization/` holds large image tiles for visual inspection. Each tile lives in a subfolder named `<Region>_[<row_start>:<row_end>-<col_start>:<col_end>]`, e.g. `Hamburg_[11000:12024-8500:9524]`.

Inside each folder, `.npy` files follow:

```text
<scale_or_format>_<product_type>.npy
```

| Prefix | Meaning |
| -------- | --------- |
| `sym`  | Linear-scale symmetrised complex (real/imag stored) |
| `linA` | Linear amplitude |
| `logI` | Log-scale intensity |

| Suffix | Meaning |
| -------- | --------- |
| `Noisy` | Raw noisy input |
| `MERLIN` | MERLIN despeckling prediction |
| `MERLIN_DDS` | MERLIN Deep Despeckling (original Hi-Paris checkpoint) |
| `ADAM_NOC` | ADAM-NOC reference despeckling |
| `DDC` | SAR-DDC pipeline output |

For `Noisy`, three files are generated: `sym_Noisy.npy` (raw complex `[H,W,2]`), `logI_Noisy.npy`, and `linA_Noisy.npy`. For all other products, `logI_` and `linA_` pairs are saved together with a `.png` preview of the `logI` version.

The `MERLIN_DDS/` subfolder stores images denoised with the original checkpoint from the [Hi-Paris deepdespeckling repository](https://github.com/hi-paris/deepdespeckling/). All visualisation files are generated by `notebooks/create_evaluation_references.ipynb`.

## Normalisation Constants

The model operates on **log-amplitude** data. A fixed affine transform normalises the signal to approximately `[0, 1]` before entering the network. Constants are defined in `src/utils/constants.py` — treat this file as the **authoritative source**.

| Constant | Value | Description |
| ---------- | ------- | ------------- |
| `EPS` | `1e-2` | Added before log to avoid `log(0)`: `log_amp = log(amplitude + EPS)` |
| `AMP_MIN` | `4.605170249938965` | ≈ p5 of `log(amplitude + EPS)` computed over the full dataset |
| `AMP_MAX` | `10.742239952087402` | ≈ p95 of `log(amplitude + EPS)` computed over the full dataset |
| `AMP_LIN_99` | `545.2018433569272` | 99th percentile of linear amplitude; used as the peak value for PSNR computation |

Normalisation formula (applied at training/inference time inside the LightningModule, **not** during preprocessing):

$$x_\text{norm} = \frac{\log(\text{amplitude} + \varepsilon) - \text{AMP\_MIN}}{\text{AMP\_MAX} - \text{AMP\_MIN}}$$

Inverse (denormalisation):

$$\text{amplitude} = \exp\!\bigl(x_\text{norm} \cdot (\text{AMP\_MAX} - \text{AMP\_MIN}) + \text{AMP\_MIN}\bigr) - \varepsilon$$

> The network reconstructs full reflectivity $r$ from a single input component. During evaluation, the Real and Imaginary network predictions are averaged (factor 0.5) to match the original intensity scale. **Metrics are computed in linear amplitude scale**; all visualisations use log-scale intensity.

The constants were derived by running `scripts/dataset/compute_stats.py` over 5 TerraSAR-X `.cos` files.

## End-to-End Full Tile Projection

Hypothetical cost of compressing the Cologne TerraSAR-X tile (21 036 × 29 828 px) with 16 px overlap between patches.

**Patch grid** — patch size 256 × 256, stride = 256 − 16 = 240 px:

```text
n_h = ceil((21036 − 16) / 240) = 88
n_w = ceil((29828 − 16) / 240) = 125
total = 88 × 125 = 11 000 patches
```

Per-patch latency and energy are taken from `results/benchmark_hardware/` (FPGA, `s1_compress.json`, MPSoC active power × latency) and `results/benchmark_unified/` (CPU/GPU, `baseline_compress_{cpu,gpu}.json`, `active_w × latency`). MERLIN's ×2 real/imag factor is already included in the per-patch measurements.

| Arch | Platform | lat/patch | total lat | nrg/patch | total energy |
| --- | --- | --- | --- | --- | --- |
| FP | FPGA s1 | 22.0 ms | 4.0 min | 214.5 mJ | 2.36 kJ |
| SH | FPGA s1 | 29.1 ms | 5.3 min | 284.6 mJ | 3.13 kJ |
| ResFP | FPGA s1 | 53.3 ms | 9.8 min | 659.5 mJ | 7.25 kJ |
| ResSH | FPGA s1 | 61.4 ms | 11.3 min | 782.5 mJ | 8.61 kJ |
| FP | CPU | 26.7 ms | 4.9 min | 2 341.8 mJ | 25.76 kJ |
| FP | GPU | 7.4 ms | 1.4 min | 866.5 mJ | 9.53 kJ |
| ResSH | CPU | 126.3 ms | 23.2 min | 12 360.7 mJ | 135.97 kJ |
| ResSH | GPU | 15.1 ms | 2.8 min | 1 862.8 mJ | 20.49 kJ |

CPU/GPU active board power is ~88–127 W vs. FPGA MPSoC ~10–13 W (~10×), so despite the GPU being ~4× faster in latency, it consumes ~4× more energy per tile than the FPGA.
